## Decisions Made

- `PatternKind` defined in `MidiSetRow.h` rather than `GenreRegistry.h` (deviation from 06.1-RESEARCH.md's own Pattern 1 code sketch, but matching the plan's explicit instruction) — keeps `MidiSetRow` free of any `GenreRegistry` dependency; `GenreRegistry.h` includes `MidiSetRow.h` instead.
- Mechanical migration mapping (RowStyle -> PatternKind/patternIndex) chosen to preserve exact row order/ids/labels/notes so the pre-existing 134-test suite required zero behavioral changes, only a type-shape update.
- `tileOnsets` takes primitive `(onsetsBeats, spanBeats, segmentLengthBeats)` arguments rather than a `RhythmVariant`, keeping `GrooveEngine.h` independent of `GenreRegistry.h`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Fixed an undocumented `RowStyle` reference outside the plan's verified blast radius**
- **Found during:** Task 1 build verification
- **Issue:** The plan's `<interfaces>` section listed the "COMPLETE list" of `RowStyle` usages (`MidiRowBuilder.cpp`, `MidiRowView.cpp`, `MidiFileWriterTests.cpp`, `MidiRowBuilderTests.cpp`), but `Tests/PluginProcessorMidiGenTests.cpp:64` also compared `a[i].style != b[i].style` inside a `rowsDeepEqual` helper — missed by the plan's own grep sweep. This broke the Task 1 build.
- **Fix:** Changed the comparison to `a[i].kind != b[i].kind`, matching the same field-rename semantics applied everywhere else.
- **Files modified:** `Tests/PluginProcessorMidiGenTests.cpp`
- **Verification:** Full suite green (142/142) immediately after.
- **Committed in:** `8364b81` (Task 1 commit)

**2. [Rule 3 - Blocking] Recovered from a shared-build-directory race with the concurrently-running 06.1-02 plan**
- **Found during:** Task 1 build verification
- **Issue:** `cmake --build build` (full target set, including the `ChordAI` plugin, not just `ChordAITests`) failed to link `ChordAI_VST3`/`ChordAI_AU`/`ChordAI_Standalone` with dozens of "symbol(s) not found" errors for core JUCE types (`juce::Component`, `juce::AudioProcessor`, etc.) that should have been present in `libChordAI_SharedCode.a`. Root cause: both this plan and plan 06.1-02 invoke `cmake --build build` against the same shared Ninja build directory; a concurrent `ar`/link step from the two overlapping builds corrupted the static archive (confirmed by `ninja`'s own `"premature end of file; recovering"` warning on `.ninja_log`, a symptom of two simultaneous Ninja processes writing the same log).
- **Fix:** Deleted the corrupted `build/ChordAI_artefacts/Debug/libChordAI_SharedCode.a` and rebuilt it in isolation (`cmake --build build --target libChordAI_SharedCode.a`), which relinked cleanly from the still-valid object files; the subsequent full `cmake --build build` then succeeded end-to-end.
- **Files modified:** None (build-artifact-only recovery, no source change)
- **Verification:** Full `cmake --build build` succeeded (VST3/AU/Standalone/ChordAITests all linked); full suite subsequently green.
- **Committed in:** N/A (build-directory recovery only, not a source commit)
