## Summary

This phase has two nearly-independent halves that share almost no code: a **music-generation half** (the user's stated top priority) and a **UI half** (locked but secondary). Both extend rather than replace Phase 5/6 infrastructure — `AnalysisResult`, beat-domain `NoteEvent`, the `analysisBroadcaster` wiring pattern, `MidiFileWriter`, and `AuditionRenderer` are all frozen contracts this phase must not touch, and every new file lives in the same `Source/MidiGen/`/`Source/UI/` folders under the same boundary rules Phase 5 established.

The music-generation half's central architectural decision is to **generalize Phase 5's five separate per-style generator functions into one data-driven pattern engine**: a `GenreSpec` is 5 `PatternArchetype`s (one per fixed slot — Sustained Chords, Rhythmic Chords, Stab/Arp, Bass Line, Top-Line Motif), each describing its rhythm grid(s), tone-set rule, register, velocity/accent shape, and a small pool of seed-selectable variants. One generic `generatePattern(AnalysisResult, PatternArchetype, seed)` function replaces `generatePopTrapRow`/`generateRnbNeoSoulRow`/`generateElectronicHouseRow`/`generateAsIsRow`. This is what makes 10 genres × 5 patterns = 50 pattern instances tractable without 50 hand-written functions, and it is what makes GEN-11's regenerate mechanic a natural fit (the seed already selects among the archetype's pre-authored, chord-tone-safe variant pool — it never needs to invent new pitches at generate time).

The second most important decision, and the one most directly serving "maximum attention to MIDI quality," is a **new groove/swing primitive that stays exactly tick-exact**. Phase 5 deliberately shipped zero timing jitter (EXP-03's bar-alignment guarantee). This phase needs genre-authentic swing (boom bap/lofi), syncopated onset grids (trap stabs, UK drill, afrobeats clave, reggaeton dembow/tresillo), and off-beat patterns (house) — all while keeping every note's `startBeats` an *exact* multiple of `1/960` of a beat, because `MidiFileWriter::kTicksPerQuarterNote = 960` is the frozen export constant. The concrete finding: 960 factors as 2⁶·3·5, so any beat-fraction with a denominator that divides 960 (halves, quarters, eighths, sixteenths, thirds, sixths, twelfths, twentieths...) lands on an exact integer tick with zero rounding. This phase's swing/syncopation constants are chosen specifically from that safe set (Pattern 5) — a concrete, testable, non-obvious technical requirement that would otherwise silently reintroduce sub-tick drift into a phase whose own north star is audio/MIDI quality.

Third, **determinism discipline from Phase 5 (Pitfall 2) extends unchanged**: regenerate must never use `juce::Random`/wall-clock seeding. The new requirement is a *reproducible, incrementable* seed — `computeBaseSeed(chordProgressionHash, genreId, patternIndex)` plus a per-row `variationCounter` that only the regenerate button increments (Pattern 4) — and harmony preservation is structural, not merely tested-for: every pattern variant is built from the *same* `ChordSegment.chord.pitchClass`/`quality` lookup on every call, so there is no code path by which regenerating could change which chord is being voiced, only *how*.

The UI half reuses the codebase's own established idioms throughout: `RegionState.h`'s ValueTree-custom-property pattern for the new `GenreState.h` (Phase-7-persistence-ready per the user's own deferred note), `MidiRowView`'s existing flat-rect pixel-glyph convention for a new regenerate icon, and — most importantly for the "premium" ask — the conveyor's *existing* low-resolution-frame + nearest-neighbour-upscale trick (`pixelScale = 4`) is the mechanism for a convincing "pixel font" with **zero new font assets**, not a new technique. The one real UI constraint this phase must solve is geometric: the existing 92×28px row gutter has no vertical room for a third stacked icon (Pattern 7's "Icon Row Geometry" — measured, not assumed, against `Tests/MidiSetsPanelLayoutTests.cpp`'s own hardcoded 92×28 fixture), so play/regenerate/save must become a horizontal row, not a vertical stack.

**Primary recommendation:** Build a single generic, data-driven pattern engine (`GenreRegistry.h/.cpp` + `PatternEngine.h/.cpp`, consuming a new `GrooveEngine.h`/`Arpeggiator.h`/`PatternSeed.h` trio of pure helpers) that replaces Phase 5's five per-style generator functions; wire `regenerateRow(index)` through the *same* `MidiSetsPanel::setRows()` full-rebuild path Phase 6 already proved safe (Pitfall D below), never a new partial-update path; and keep every swing/syncopation constant a beat-fraction whose denominator divides 960.

### Pattern 1: `PatternArchetype`/`GenreSpec` data model — the genre library as data, not code

**What:** Every genre is exactly 5 `PatternArchetype`s, one per fixed `PatternKind` slot. A slot's *meaning* (Sustained/Rhythmic/Stab/Bass/TopLine) stays constant across every genre — only its rhythm, tone-set, register, and velocity shape vary. This directly implements the "точний склад 5 патернів на жанр" Claude's-discretion item with one consistent taxonomy.

```cpp
// Source/MidiGen/GenreRegistry.h
#pragma once
#include "../Analysis/AnalysisResult.h"
#include <array>
#include <vector>

// Position in every genre's fixed 5-slot layout. Order is stable and used as
// the row's patternIndex (0-4) -- the same index regenerateRow(index) targets
// and the same index MidiRowView colour-codes by (accentForKind), so a chord
// row's visual identity/position stays consistent across a genre switch.
enum class PatternKind { SustainedChords, RhythmicChords, StabArp, BassLine, TopLineMotif };

enum class ToneSetKind { Triad, SeventhExtension, PowerChord, SingleTopTone, DiatonicMotif };

// One concrete rhythmic shape a slot can use. Multiple RhythmVariants in a
// pool are how regenerate (GEN-11) picks a different, still-genre-authentic
// rhythm without touching harmony -- see Pattern 4.
struct RhythmVariant
{
    std::vector<double> onsetsBeats;  // exact beat-fraction offsets within one repeating span,
                                       // relative to the CURRENT chord segment's own start (Phase 5
                                       // Pattern 3 precedent: segment-relative, not global-bar-relative)
    double spanBeats = 4.0;           // the span onsetsBeats repeats across, tiled over the segment
    double noteLengthRatio = 0.9;     // fraction of the inter-onset gap (staccato < 1.0, legato ~1.0)
};

struct PatternArchetype
{
    PatternKind kind = PatternKind::SustainedChords;
    ToneSetKind toneSet = ToneSetKind::Triad;

    int registerAnchor = 60;          // MIDI anchor note (see ChordToneMapper.h's rootMidiNote convention)
    int registerLow = 48, registerHigh = 72;  // voice-leading clamp band (only used when toneSet
                                               // needs cross-chord continuity, e.g. SeventhExtension)
    bool dropRoot = false;            // trap-style "leave the root for the bass row" flag

    std::vector<RhythmVariant> rhythmPool;    // >=1; seed % pool.size() selects (Pattern 4)
    std::vector<int> octaveOffsetPool = { 0 }; // seed-selectable register variety, semitone multiples of 12

    float baseVelocity = 0.75f;
    std::vector<float> accentPattern = { 1.0f }; // per-onset multiplier, cyclic across a span's onsets
    float jitterRange = 0.08f;                    // reuses Humanization.h's deterministicJitter, unchanged
    float ornamentProbability = 0.0f;             // 0..1, TopLineMotif-only diatonic passing-tone insertion (Pattern 3)
};

struct GenreSpec
{
    juce::String id, label;
    std::array<PatternArchetype, 5> patterns; // index == (int) PatternKind
};

const std::vector<GenreSpec>& allGenres();
const GenreSpec* findGenre (const juce::String& id); // nullptr if unknown -- caller must handle (Pitfall below)

// Product-design default (Claude's discretion): direct continuity from Phase
// 5's existing 3 styles + bass, plus the user's own first two example genres.
inline const juce::StringArray kDefaultMainGenreIds { "trap", "uk-drill", "boom-bap", "rnb-neosoul", "house" };
```

**When to use:** `GenreRegistry.cpp` builds all 10 menu `GenreSpec`s (Pattern 3's concrete per-genre tables below) as free functions (`buildTrapSpec()`, `buildUkDrillSpec()`, ...) assembled into `allGenres()`'s static vector.

### Pattern 2: `MidiSetRow` reshape — `PatternKind` + stable `patternIndex` replace `RowStyle`

**What:** `RowStyle` (`DetectedAsIs`/`PopHipHopTrap`/`RnbNeoSoul`/`ElectronicHouse`/`Bass`) described *which of 5 fixed styles*; that concept no longer exists (the 5 genre patterns replace the fixed set, per the user's locked decision). Replace it with `PatternKind` (slot meaning, stable across every genre switch) plus an explicit `patternIndex` (0-4) so `regenerateRow(index)` and `MidiRowView`'s regenerate-icon click both have an unambiguous, row-order-independent target — matching how `row.id`/`row.style` already self-describe identity today rather than relying on array position.

```cpp
// Source/MidiGen/MidiSetRow.h (reshaped)
struct MidiSetRow
{
    juce::String id;       // "<genreId>-<slotSlug>", e.g. "trap-sustained", "trap-stab-arp"
    juce::String label;    // "Trap — Sustained Chords" (display; MidiFileWriter uses id, never label, for filenames -- unchanged rule)
    PatternKind kind = PatternKind::SustainedChords;
    int patternIndex = 0;  // 0-4, stable slot index -- the regenerateRow(index) target
    std::vector<NoteEvent> notes;
};
```

**Verified contained blast radius** (grep across `Source/` and `Tests/`): only `MidiRowView.cpp` (`accentForStyle` → rename `accentForKind`, switch on `PatternKind`), `MidiRowBuilder.cpp`, and two test files (`MidiFileWriterTests.cpp`, `MidiRowBuilderTests.cpp`) reference `RowStyle` today. `MidiFileWriter.cpp`, `AuditionRenderer.cpp/.h`, `MidiSetsPanel.cpp` all touch only `row.notes`/`row.id`/`row.label` — zero changes needed there beyond the type recompiling.

### Pattern 3: The generic pattern engine (the "core groove/pattern engine" this phase is really about)

**What:** One function replaces `generateAsIsRow`/`generatePopTrapRow`/`generateRnbNeoSoulRow`/`generateElectronicHouseRow` (Phase 5's `generateBassRow` is instead *called from inside* the Bass-slot case, reusing its existing `BassRhythm` shapes as `RhythmVariant` sources — see Pattern 10).

```cpp
// Source/MidiGen/PatternEngine.h
#pragma once
#include "../Analysis/AnalysisResult.h"
#include "GenreRegistry.h"
#include "NoteEvent.h"
#include <vector>
#include <cstdint>

// Pure function: same (AnalysisResult, PatternArchetype, seed) always produces
// byte-identical output (GEN-04/GEN-11's shared determinism contract). Every
// pitch comes from ChordToneMapper.h's triadIntervals/rnbExtensionIntervals
// (or the new diatonicScaleIntervals for TopLineMotif ornaments) applied to
// the SAME segment.chord.pitchClass/quality on every call -- seed only ever
// selects among pre-authored rhythm/octave/ornament variants, never invents
// a pitch (this is what makes harmony-preservation structural, not tested-in).
std::vector<NoteEvent> generatePattern (const AnalysisResult& result,
                                         const PatternArchetype& archetype,
                                         uint32_t seed);
```

**Internal shape** (illustrative, per-segment loop -- mirrors Phase 5 Pattern 3's `chunkSegment`, generalized):
```cpp
// Source/MidiGen/PatternEngine.cpp (shape)
for (const auto& segment : result.chords)
{
    if (segment.chord.quality == ChordQuality::NoChord)
        continue; // Pitfall 1 (05-RESEARCH.md) still applies, unchanged, in every slot

    // 1. Tone set: triad/extension/power-chord/single-top-tone per archetype.toneSet,
    //    optionally with dropRoot (trap: omit the root, extensions/3rd/7th only).
    auto intervals = toneSetIntervals (archetype.toneSet, segment.chord.quality, archetype.dropRoot);

    // 2. Register: registerAnchor + seed-selected octaveOffsetPool entry, OR
    //    (for SeventhExtension) VoiceLeadingEngine.h's existing nearestOctaveNote
    //    against the previous voiced chord's mean pitch -- same mechanism as
    //    Phase 5's R&B row, now reusable by ANY genre whose archetype opts in.
    auto pitches = /* ChordToneMapper.h::intervalsToMidiNotes + register logic */;

    // 3. Rhythm: archetype.rhythmPool[seed % archetype.rhythmPool.size()], tiled
    //    across the segment via GrooveEngine.h (Pattern 5), segment-relative.

    // 4. Velocity: archetype.baseVelocity * archetype.accentPattern[onsetIndex % pattern.size()]
    //    + Humanization.h::deterministicJitter(noteIndex, seed, archetype.jitterRange) -- SAME
    //    proven per-note hash, now also seeded by the regenerate variation (Pattern 4).

    // 5. TopLineMotif only: archetype.ornamentProbability seed-thresholds an optional
    //    diatonic passing tone from ChordToneMapper.h::diatonicScaleIntervals(result.key.isMajor)
    //    anchored at result.key.tonicPitchClass -- the ONLY place a note can be a
    //    non-chord-tone, and even then constrained to the detected KEY's diatonic
    //    scale, never a fully chromatic passing tone (keeps the harmony-preservation
    //    test crisp: every note ∈ chord tones ∪ diatonic scale of AnalysisResult.key).
}
```

**When to use:** Every one of the 50 (10 genres × 5 slots) pattern instances is this same function called with a different `PatternArchetype`. Slot-specific *behavior differences* (e.g. Bass reusing `BassLineGenerator.h`'s `BassRhythm` shapes, TopLineMotif's ornament step) are `PatternKind`-gated inside this one function, not separate functions — keeps the "don't hand-roll 50 near-duplicates" property from the Alternatives table.

### Pattern 4: Deterministic seed & regenerate model (GEN-11)

**What:** Two-level seed: a **base seed** derived only from stable, already-integer `AnalysisResult` fields (never floats — avoids any bit-pattern-hashing fragility) plus the genre/pattern identity, and a **variation counter** that only increments on a regenerate click.

```cpp
// Source/MidiGen/PatternSeed.h
#pragma once
#include "../Analysis/AnalysisResult.h"
#include <cstdint>

// Hashes only INTEGER-valued, already-stable fields (pitchClass, quality cast
// to int, startBeatIndex, endBeatIndex) -- never bpm/startSeconds (doubles),
// sidestepping any floating-point hash-stability question entirely. Same
// Knuth-multiplicative-hash shape as Humanization.h::deterministicJitter
// (05-RESEARCH.md Pattern 5), reused for a new purpose.
inline uint64_t hashChordProgression (const AnalysisResult& result)
{
    uint64_t h = 0x9e3779b97f4a7c15ull; // fixed constant, NOT wall-clock/address-derived
    for (const auto& seg : result.chords)
    {
        uint64_t v = ((uint64_t) seg.chord.pitchClass << 40)
                    ^ ((uint64_t) seg.chord.quality << 32)
                    ^ ((uint64_t) (uint32_t) seg.startBeatIndex << 16)
                    ^ (uint64_t) (uint32_t) seg.endBeatIndex;
        h ^= v + 0x9e3779b97f4a7c15ull + (h << 6) + (h >> 2); // boost-style combine
    }
    return h;
}

inline uint64_t computeBaseSeed (const AnalysisResult& result, const juce::String& genreId, int patternIndex)
{
    uint64_t h = hashChordProgression (result);
    h ^= (uint64_t) genreId.hashCode() * 2654435761ull;
    h ^= (uint64_t) patternIndex * 0x100000001b3ull;
    return h;
}

// Combines the base seed with a per-row, click-incremented variation counter
// into the 32-bit seed generatePattern()/deterministicJitter() consume.
inline uint32_t combineSeedWithVariation (uint64_t baseSeed, uint32_t variationCounter)
{
    uint64_t h = baseSeed ^ ((uint64_t) variationCounter * 0xff51afd7ed558ccdull);
    h ^= h >> 33; h *= 0xc4ceb9fe1a85ec53ull; h ^= h >> 33; // MurmurHash3 finalizer shape
    return (uint32_t) h;
}
```

```cpp
// Source/MidiGen/MidiRowBuilder.h -- API surface this phase adds
std::vector<MidiSetRow> generateGenreRows (const AnalysisResult&, const GenreSpec&, const GenerationSettings& = {});

// Regenerates ONE row's notes only (variationCounter is the CALLER's -- caller,
// i.e. PluginProcessor, owns the per-patternIndex counter and bumps it BEFORE
// calling this). Returns the row for patternIndex only.
MidiSetRow regenerateRow (const AnalysisResult&, const GenreSpec&, int patternIndex,
                           uint32_t variationCounter, const GenerationSettings& = {});
```

**What varies with the seed (harmony-preserving by construction):**
1. **Rhythm-pattern selection** — `archetype.rhythmPool[seed % archetype.rhythmPool.size()]`. Every genre's `RhythmVariant` pool (2-4 entries recommended per slot) is authored up front (Pattern 3's per-genre tables); regenerate only picks among them.
2. **Octave/inversion choice** — `archetype.octaveOffsetPool[seed2 % pool.size()]`, always ±12/±24 semitone multiples (or, for extension chords, an alternative *inversion* — same pitch classes, different tone-to-octave assignment via `nearestOctaveNote`'s existing register clamp), always within `registerLow`/`registerHigh`.
3. **Ornament density** — `archetype.ornamentProbability` seed-thresholded (TopLineMotif slot only), constrained to the detected key's diatonic scale (Pattern 3, step 5).

**When to use:** `PluginProcessor::regenerateRow(int patternIndex)` bumps `patternVariationCounters[patternIndex]`, calls `MidiRowBuilder::regenerateRow(...)`, splices the single returned `MidiSetRow` into a **copy** of the current 5-row vector at that index, and publishes the new vector via the same `std::atomic_store` + `analysisBroadcaster.sendChangeMessage()` idiom `triggerAnalysis()`'s `onDone` already uses.

### Pattern 5: Tick-exact swing/groove — the concrete "quality" technical requirement

**What:** `MidiFileWriter::kTicksPerQuarterNote = 960` is the frozen export resolution (`Source/MidiGen/MidiFileWriter.h`, verified). `960 = 2^6 · 3 · 5`. Any beat-fraction whose denominator divides 960 lands on an **exact integer tick** — zero rounding, byte-identical re-export every time. This phase's swing/syncopation constants are chosen from that safe set on purpose:

| Ratio | Value | Denominator | Divides 960? | Genre use |
|-------|-------|--------------|---------------|-----------|
| Straight | 1/2 = 0.5 | 2 | Yes (960/2=480) | House, techno, pop, afrobeats base grid |
| Light swing | 7/12 ≈ 0.5833 | 12 | Yes (960/12=80) | Boom bap / lofi ("54-62% MPC swing" production convention, represented as the nearest clean rational) |
| Heavy/triplet swing | 2/3 ≈ 0.6667 | 3 | Yes (960/3=320) | UK drill 32nd-roll feel, trap triplet stabs |
| Dotted-eighth (tresillo unit) | 3/4 = 0.75 beat | 4 | Yes (960/4=240) | Reggaeton dembow/tresillo `{0, 0.75, 1.5}`, trap 808 anticipation |
| Sixteenth | 1/4 = 0.25 beat | 4 | Yes | House stabs (existing `kHouseStabOffsetsBeats`, unchanged), afrobeats clave-ish grids |

```cpp
// Source/MidiGen/GrooveEngine.h
#pragma once
#include <vector>

// Named, tick-safe constants -- see the ratio table above for why each one
// was chosen (denominator divides MidiFileWriter::kTicksPerQuarterNote=960).
inline constexpr double kSwingStraight = 0.5;
inline constexpr double kSwingLight    = 7.0 / 12.0;  // ~58%, boom bap/lofi
inline constexpr double kSwingTriplet  = 2.0 / 3.0;   // true triplet, UK drill/trap

// Delays the SECOND sixteenth of each eighth-note pair by swingRatio of the
// eighth's span. sixteenthIndexInBeat: 0-3 (four 16ths per beat). Straight
// (kSwingStraight) reproduces the unswung grid exactly (0, 0.25, 0.5, 0.75).
inline double swingSixteenthOffsetBeats (int sixteenthIndexInBeat, double swingRatio)
{
    const int pairIndex = sixteenthIndexInBeat / 2;         // which 8th-note pair (0 or 1)
    const bool isSecondOfPair = (sixteenthIndexInBeat % 2) == 1;
    const double pairStartBeats = pairIndex * 0.5;
    return pairStartBeats + (isSecondOfPair ? swingRatio * 0.5 : 0.0);
}

// The general primitive: an explicit, genre-authored list of onset beat-offsets
// within one repeating span (tresillo/dembow/clave/off-beat-stab patterns are
// this, not a swing formula -- see Alternatives Considered). Mirrors
// RhythmVariant.onsetsBeats/spanBeats exactly; this struct is what
// PatternArchetype.rhythmPool actually stores.
struct OnsetGrid
{
    std::vector<double> onsetsBeats;
    double spanBeats = 4.0;
};
```

**Open Question (flagged, not asserted):** whether `juce::MidiMessageSequence::addEvent`/`MidiFile::writeTo` rounds or truncates a fractional tick timestamp could not be confirmed from official docs alone (no JUCE source was consulted). Because every constant above is chosen to be tick-exact by construction, this is defense-in-depth, not a blocking unknown — but Wave 1 should add one concrete regression test (`GrooveEngineTests.SwingOffsetsRoundTripExactTicksThroughMidiFileWriter`): build a `NoteEvent` at a swung offset, run it through the *existing* `MidiFileWriter::buildMidiFile`, and assert the written tick position equals `juce::roundToInt(startBeats * 960)` exactly — closing the loop empirically rather than trusting the arithmetic alone.

### Anti-Patterns to Avoid

- **Writing 50 near-duplicate generator functions** (10 genres × 5 slots) instead of one data-driven engine (Pattern 3) — the single biggest risk to "maximum quality," since a fix/tuning pass would need to be independently repeated in every duplicate.
- **Letting the regenerate seed touch pitch class or chord quality** — every seed-varied choice (Pattern 4) must be selected from a pool built from the SAME `segment.chord` lookup; never let seed influence which `AnalysisResult.chords[i]` a note reads from or reinterpret `quality`.
- **Arbitrary decimal swing percentages** (e.g. a literal `0.58`) instead of a rational fraction whose denominator divides 960 (Pattern 5) — silently reintroduces the exact sub-tick drift class of bug Phase 5 deliberately avoided by working in beat units at all.
- **A second, "lighter" row-update path for regenerate** that bypasses `MidiSetsPanel::setRows()` — Phase 6's Pitfall 3 (every `MidiRowView` must be destroyed/recreated together, playing-row state lives on the processor, not the view) was hard-won; a single-row-mutation shortcut would need to independently re-derive that same safety invariant instead of reusing the already-proven one.
- **`juce::PopupMenu` for the genre selector** — breaks the locked pixel-art visual identity and fights JUCE's default single-click-dismiss behavior for a multi-toggle UX (see Alternatives Considered).

## Common Pitfalls

### Pitfall A: Seed touching harmony instead of only presentation
**What goes wrong:** A regenerate click that ends up changing the actual chord being voiced (wrong root, wrong quality) instead of just its rhythm/register/ornament — silently breaks the "harmony preserved" locked decision and would be very hard to notice by ear on an unfamiliar progression.
**Why it happens:** Easy to accidentally let a seed value index into `result.chords` itself, or perturb `segment.chord.pitchClass`/`quality` directly, if the pattern-generation loop and the seed-selection logic aren't kept strictly separate.
**How to avoid:** `generatePattern()` (Pattern 3) always re-reads `segment.chord.pitchClass`/`quality` fresh from the *same* `AnalysisResult.chords` on every call, at every seed value — seed only ever indexes into `archetype.rhythmPool`/`octaveOffsetPool`/the ornament threshold, never into the chord sequence itself. Enforce with a dedicated `PatternEngineTests.HarmonyPreservationAcrossVariations` test: for a fixed fixture, generate `variationCounter` 0 through 20, assert every note's pitch-class (mod 12) is a member of that segment's chord-tone set (or, for TopLineMotif, the chord-tone-or-diatonic-scale set) on every single variation.
**Warning signs:** A regenerate click that audibly changes which chord is playing, not just how it's voiced.

### Pitfall B: Non-deterministic regeneration (extends 05-RESEARCH.md Pitfall 2)
**What goes wrong:** Same class of bug as Phase 5's Pitfall 2 (wall-clock/mutable-state RNG breaking reproducibility) — now with a second failure mode: forgetting to persist `patternVariationCounters` correctly means a regenerate click could accidentally regenerate to the SAME variation instead of a new one (counter not actually incremented before use), or, worse, use `juce::Random` "just for the new randomize feature" since the word "randomizer" is literally in the user's own request.
**Why it happens:** The feature is explicitly named "рандомізатор" (randomizer) by the user, which is a strong pull toward reaching for `juce::Random`/`std::mt19937` even though the actual requirement (GEN-11) explicitly demands determinism.
**How to avoid:** `PatternSeed.h`'s `combineSeedWithVariation` (Pattern 4) is the ONLY randomness-shaped code allowed anywhere in this feature's path; a dedicated `PluginProcessorGenreTests.RegenerateIsDeterministicGivenSameCounter` test constructs two processors, drives both through the identical sequence of `regenerateRow(0)` calls, and asserts byte-identical resulting rows.
**Warning signs:** A `juce::Random`/`std::mt19937`/`std::random_device` anywhere under `Source/MidiGen/` or in the genre/pattern code paths; a regenerate test that passes once and fails intermittently.

### Pitfall C: Swing/syncopation ratios that don't divide 960 cleanly (this phase's own novel pitfall — see Pattern 5)
**What goes wrong:** An arbitrary decimal swing/groove constant (picked "because it sounded like a production article's number," e.g. a literal `0.58`) produces a fractional tick position on export, which — depending on how `juce::MidiFile`/`MidiMessageSequence` actually handle non-integer timestamps internally (unconfirmed from docs alone, see Pattern 5's Open Question) — risks tiny, possibly non-reproducible rounding at the SMF-byte level, undermining the "same input always produces byte-identical output" testing discipline this whole codebase relies on (Phase 5 Pitfall 2's determinism tests, `MidiFileWriterTests`' own byte-identical-output convention).
**Why it happens:** Production-technique research naturally surfaces percentage numbers (54%, 58%, 62%, 66.7%) that don't obviously map to "does this divide 960 evenly" without deliberately checking.
**How to avoid:** Every swing/onset constant in `GrooveEngine.h`/every genre's `RhythmVariant.onsetsBeats` must be a rational fraction of a beat whose denominator divides 960 (Pattern 5's table) — checked once, applies everywhere, and is itself unit-testable (`GrooveEngineTests.AllNamedSwingConstantsDivide960Exactly`, a compile-time or startup-time sweep over every genre's rhythm pools asserting `std::fmod(onsetBeats * 960.0, 1.0) < epsilon` for every onset in every `RhythmVariant` in `allGenres()`).
**Warning signs:** Any swing/groove numeric literal introduced during genre-tuning that wasn't checked against the divides-960 table.

### Pitfall D: Regenerate bypassing the proven full-rebuild row-update path
**What goes wrong:** A tempting "optimization" — mutate just the one changed `MidiRowView` in place instead of going through `MidiSetsPanel::setRows()`'s existing destroy-and-recreate-all-5-views path — would silently re-open Phase 6's already-solved Pitfall 3 (playing-row audition state must never live on a view; a regenerate must stop any in-flight audition the same way a region-change regenerate already does).
**Why it happens:** Regenerating "just one row" naturally suggests updating "just one view" — the existing full-rebuild-on-any-change design isn't obvious from the regenerate feature's own description alone.
**How to avoid:** `PluginProcessor::regenerateRow()` publishes a full 5-element `midiSetRows` vector (Pattern 6's Code Example splices one element into a *copy* of the current vector) through the *exact same* `analysisBroadcaster` → `MidiSetsPanel::setRows()` path every other row-set change already uses — no new update path, no new Pitfall-3-shaped bug surface.
**Warning signs:** A new `MidiRowView::updateRow()`/`MidiSetsPanel::updateSingleRow()` method appearing anywhere in a plan — that shape is very likely reintroducing Pitfall 3.

### Pitfall E: Icon-row geometry regression (measured, see Pattern 7)
**What goes wrong:** Assuming the existing 92×28px gutter has room for a third stacked icon (it does not — `12*3 + 2*2 = 40px > 28px` row height) and discovering the overlap only visually/at runtime instead of from the existing test fixture.
**Why it happens:** The old vertical-pair math (`pairHeight = kIconSize*2 + kIconGap = 26`, just barely under 28) looks like it has "2px of headroom," which is easy to misread as "room for one more small thing" without doing the actual third-icon arithmetic.
**How to avoid:** `Tests/MidiSetsPanelLayoutTests.cpp`'s own hardcoded `juce::Rectangle<int> gutter (0, 0, 92, 28)` fixture is the ground truth — any new icon-geometry design must pass a rewritten version of `IconRectsFitInsideGutterAndDoNotOverlap` against that exact 92×28 shape, horizontal-row layout (Pattern 7), before it's considered correct.
**Warning signs:** A vertical 3-icon stack anywhere in a plan or its diffs.

### Pitfall F: Unknown genre id reaching `findGenre()`
**What goes wrong:** `GenreState::readActiveGenre` could return a stale/foreign genre id (e.g. a project saved with a future version's genre that this build doesn't know, or corrupt XML) that `GenreRegistry::findGenre()` can't resolve, returning `nullptr` — if callers assume non-null, this is a null-pointer crash on session load.
**Why it happens:** `apvts.state`-backed custom properties are plain strings with no schema validation (same class of risk `RegionState::clampRegion`'s own defensive design already anticipates for region bounds).
**How to avoid:** Every `findGenre()` call site (Pattern 6's `triggerAnalysis` onDone, `setActiveGenre`) treats `nullptr` as "fall back to `kDefaultMainGenreIds[0]` (`"trap"`)," never as an unreachable case; a `PluginProcessorGenreTests.UnknownActiveGenreIdFallsBackSafely` test constructs a processor with a hand-corrupted `apvts.state` genre property and asserts no crash + a valid non-empty row set.
**Warning signs:** Any `findGenre(...)->` dereference without a preceding null check.

### Concrete Trap `GenreSpec` (fully worked example)

Grounded in cross-verified production research (Unison Audio, Chordoo, eMastered — see Sources): dark/minor tonality is inherited automatically from the *detected* chord quality (this phase never forces a key/quality — same "genre-authentic voicing of the actual detected progression" differentiator FEATURES.md already documents for Phase 5); "leave the root for the 808" is `dropRoot = true` on the upper voicings; sparse, syncopated, staccato-leaning.

```cpp
// Source/MidiGen/GenreRegistry.cpp (shape)
GenreSpec buildTrapSpec()
{
    GenreSpec spec;
    spec.id = "trap"; spec.label = "Trap";

    // Slot 0: SustainedChords -- root-dropped triad/7th (extensions/3rd/7th
    // only, per "drop the root, play 3rd/7th/extensions up top" research
    // finding), C3 anchor (kAnchorPopTrap precedent), shortened length
    // (staccato -- "long sustains clash with the 808").
    auto& sustained = spec.patterns[(size_t) PatternKind::SustainedChords];
    sustained.toneSet = ToneSetKind::Triad;
    sustained.dropRoot = true;
    sustained.registerAnchor = kAnchorPopTrap; // 48, existing ChordToneMapper.h constant
    sustained.rhythmPool = { RhythmVariant { { 0.0 }, /*spanBeats*/ 4.0, /*noteLengthRatio*/ 0.85 } };
    sustained.baseVelocity = 0.75f; sustained.jitterRange = 0.05f;

    // Slot 1: RhythmicChords -- half-bar re-strike (Phase 5's existing
    // Pop/Trap pattern), now with a light staccato + strong/weak accent.
    auto& rhythmic = spec.patterns[(size_t) PatternKind::RhythmicChords];
    rhythmic.toneSet = ToneSetKind::Triad;
    rhythmic.registerAnchor = kAnchorPopTrap;
    rhythmic.rhythmPool = { RhythmVariant { { 0.0, 2.0 }, 4.0, 0.9 } };
    rhythmic.accentPattern = { 1.0f, 0.7f };
    rhythmic.baseVelocity = 0.78f; rhythmic.jitterRange = 0.06f;

    // Slot 2: StabArp -- syncopated dotted-8th stabs (tick-exact, Pattern 5),
    // root-dropped extensions only.
    auto& stab = spec.patterns[(size_t) PatternKind::StabArp];
    stab.toneSet = ToneSetKind::SeventhExtension; stab.dropRoot = true;
    stab.registerAnchor = 60;
    stab.rhythmPool = {
        RhythmVariant { { 0.0, 0.75, 1.5, 2.5 }, 4.0, 0.3 },   // variant A
        RhythmVariant { { 0.0, 1.5, 2.25, 3.0 }, 4.0, 0.3 },   // variant B -- regenerate picks between these
    };
    stab.baseVelocity = 0.82f; stab.jitterRange = 0.1f;

    // Slot 3: BassLine -- delegates to BassLineGenerator.h's existing
    // TrapSustain shape inside PatternEngine's PatternKind::BassLine case
    // (Pattern 10) -- no new rhythm data needed here beyond a marker.
    spec.patterns[(size_t) PatternKind::BassLine].registerAnchor = kAnchorBass; // 36

    // Slot 4: TopLineMotif -- sparse syncopated single-tone motif, dark/cinematic.
    auto& top = spec.patterns[(size_t) PatternKind::TopLineMotif];
    top.toneSet = ToneSetKind::SingleTopTone;
    top.registerAnchor = 72;
    top.rhythmPool = { RhythmVariant { { 0.0, 1.5 }, 4.0, 0.6 } };
    top.baseVelocity = 0.7f; top.jitterRange = 0.08f; top.ornamentProbability = 0.15f;

    return spec;
}
```

### `toneSetIntervals` — the one dispatcher every slot's tone-set rule goes through

```cpp
// Source/MidiGen/ChordToneMapper.h -- EXTENSION (new function alongside the
// existing triadIntervals/rnbExtensionIntervals, which are both reused as-is)
inline std::vector<int> diatonicScaleIntervals (bool isMajor)
{
    // Natural minor / major, matches AnalysisResult.h's KeyResult.isMajor convention.
    return isMajor ? std::vector<int> { 0, 2, 4, 5, 7, 9, 11 }
                    : std::vector<int> { 0, 2, 3, 5, 7, 8, 10 };
}

inline std::vector<int> powerChordIntervals() { return { 0, 7 }; } // root + fifth, techno/reggaeton

inline std::vector<int> toneSetIntervals (ToneSetKind kind, ChordQuality quality, bool dropRoot)
{
    std::vector<int> intervals;
    switch (kind)
    {
        case ToneSetKind::Triad:            intervals = triadIntervals (quality); break;
        case ToneSetKind::SeventhExtension: intervals = rnbExtensionIntervals (quality); break;
        case ToneSetKind::PowerChord:       intervals = powerChordIntervals(); break;
        case ToneSetKind::SingleTopTone:    intervals = { triadIntervals (quality).empty() ? 0 : triadIntervals (quality).back() }; break;
        case ToneSetKind::DiatonicMotif:    intervals = { 0 }; break; // caller supplies the specific scale-degree per onset
    }
    if (dropRoot && intervals.size() > 1)
        intervals.erase (intervals.begin()); // drop the 0 (root) interval, keep the rest
    return intervals;
}
```

## Open Questions

1. **Whether `juce::MidiFile`/`MidiMessageSequence` round or truncate fractional tick timestamps** (Pattern 5)
   - What we know: every swing/onset constant this phase introduces is chosen to be exactly tick-representable against `kTicksPerQuarterNote=960`, so this should be moot in practice.
   - What's unclear: could not confirm the exact internal rounding behavior from official docs alone (would need JUCE source inspection).
   - Recommendation: add `GrooveEngineTests.SwingOffsetsRoundTripExactTicksThroughMidiFileWriter` (Pattern 5) in Wave 1 as an empirical closing test rather than blocking on source inspection now.

2. **Genre selector "exactly 5" interaction model — FIFO auto-swap vs. explicit Done-gated checkbox list** (Pattern 8)
   - What we know: both satisfy "рівно 5" as a final state; they differ in moment-to-moment UX and implementation shape.
   - What's unclear: which one matches what the user actually pictured — "checkboxes... лише 5" reads ambiguously between "hard live cap" (FIFO-swap) and "must select exactly 5 before it takes effect" (Done-gated).
   - Recommendation: FIFO-swap (Pattern 8's primary recommendation) as the default plan, but flag explicitly for a one-line confirmation at plan-check before Wave 4 locks it in — cheap to ask now, expensive to rebuild later.

3. **Whether the idle "drop song or melody here" text should persist after a song has already been successfully loaded/analyzed, or only show pre-first-load** (Architecture Pattern 9 in the additional-context's numbering, addressed inline above)
   - What we know: the user's phrasing describes the idle *state* generically (stopped belt + text whenever not dragging/analyzing), with no explicit carve-out for "after a file has ever been loaded."
   - What's unclear: whether showing "drop song or melody here" is intended to persist as a standing invitation for the *next* drop even once a track is loaded, or should disappear for the rest of the session once the first load succeeds.
   - Recommendation: implement the literal, simpler reading (idle = stopped + text whenever `! dragHover && ! analyzing`, unconditionally, matching UI-01's own success-criterion wording "idle conveyor is stopped and shows...") and flag it for the human checkpoint (same review moment as the "premium look" ear/eye check) rather than gating implementation on it now.

4. **Exact per-genre numeric defaults (velocities, jitter ranges, specific onset lists beyond the tick-exactness constraint) are product/design defaults, not locked facts** — identical caveat to 05-RESEARCH.md's own Open Question 2, now extended to 10 genres × 5 slots.
